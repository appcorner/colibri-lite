# M6.3-01 Precision and Backend Candidate Proposal

## Proposed candidate

`cpu-safe-rust-int8-group128-layer0-v1` is the sole M6.3 candidate:

| Dimension | Decision |
| --- | --- |
| Scope | Qwen3-30B-A3B Layer 0 routed experts only |
| Weight storage | Symmetric INT8 in input groups of 128; F32 scale for each output-row/group |
| Kernel | Safe scalar Rust, direct INT8-and-scale consumption, F32 activation and accumulation |
| Preserved F32 operations | Router, norms, routing weights, attention, residuals, softmax, cache, dense tensors, LM head |
| New dependencies | None |
| Unsafe / FFI / SIMD | None |
| Status | Experimental M6.3 slice only; not a promoted backend or precision policy |

For each projection, M6.3-02 will process quantized values in the same
column/group order as the F32 reference and apply the group scale inside the
accumulation loop. A complete F32 projection/expert buffer is forbidden in the
candidate's normal execution path. The existing F32 path remains independently
executable for comparison.

## Why this candidate

The M6.1 hardware profile records CPU/RAM/SSD evidence but marks CUDA,
DirectML, and Vulkan unavailable with zero VRAM budget. A GPU proposal would
therefore be unsupported. The measured safe scalar F32 matrix-vector median is
`1.8614 GFLOP/s`; this proposal makes no extrapolated tok/s claim from that
measurement.

The historical group-128 study has the lowest representative weighted output
error (`0.0820999`) among the three recorded INT8 layouts, compared with
`0.1043549` for the per-output-channel layout. It has a modeled `4.085321x`
F32-expert compression, but costs 2.81% more bytes than the prior candidate.
That prior candidate was rejected as `quality_risk` after propagated error and
a Thai argmax change, so it is not reused.

Layer 0 is selected because its incoming hidden state comes from the unchanged
F32 path. This makes the first divergence attributable to the candidate rather
than accumulated lower-precision state. It does not make the candidate safe for
the remaining 47 layers.

## Dependency, license, unsafe, and provenance review

- Dependencies: no crate is proposed; standard-library arithmetic and existing
  workspace types are sufficient. This keeps `clr-core` dependency-free and
  avoids a transitive unsafe/native-library surface.
- Unsafe: no unsafe code or public unsafe API is proposed. The workspace's
  forbidden-unsafe lint remains unchanged.
- License: model-derived data remains tied to the pinned Apache-2.0 Qwen source
  contract in ADR 0011. The design is an independent implementation and does
  not vendor or copy third-party runtime code.
- Provenance: the future additive artifact must cite the F32 root manifest,
  upstream revision, conversion command/tool versions, source/output hashes,
  layout fields, and generation time. No large artifact is generated by this
  proposal.

## Required gates and stop conditions

Before M6.3-06 can approve expansion, M6.3-02 through M6.3-05 must prove:

1. direct consumption without whole-projection/expert F32 expansion;
2. exact structural identity and F32-safe router IDs;
3. documented checkpoint/logit comparison, deterministic English and Thai
   fixtures, and unchanged F32 comparison path;
4. repeated cold/warm throughput, TTFT, RAM, physical reads, cache behavior,
   and bytes/token; and
5. a material benefit without exceeding the admitted budget or relying on swap.

Any router safe-margin mismatch, undocumented tolerance, artifact/provenance
failure, unsafe/dependency need, or non-repeatable benefit stops the slice and
requires review. The M4.3 group-128 evidence is directional only; it is not a
substitute for these gates.
