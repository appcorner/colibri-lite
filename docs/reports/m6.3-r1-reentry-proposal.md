# M6.3-R1 Re-entry Proposal: Measurable Quantized Vertical Slice

## Status

**Proposed for review; not authorized for implementation.**

This proposal does not overturn the M6.3-06 NO-GO decision, reopen M6.4, or
admit a new precision format.  It defines the smallest reviewed re-entry that
could produce the missing numerical-quality, physical-I/O, and process
working-set evidence without weakening `reference-f32-v1`.

## Why a new proposal is required

The stopped `cpu-safe-rust-int8-group128-layer0-v1` candidate established
direct consumption and preserved frozen router/token outcomes, but failed for
three independent reasons:

1. its English fixed-logit drift (`1.69116020202636719e-1`) had no justified
   candidate admission rule;
2. a single changed layer could not produce material whole-runtime throughput
   while Layers 1--47 remained scalar F32; and
3. the report carried logical byte accounting, not process working-set peaks
   or physical storage evidence.

This proposal treats those as gates to measure, not as quantities to infer.
It also records an unavoidable plan conflict: the current M6.3 scope is one
layer, whereas its stop condition requires repeatable material end-to-end
benefit.  The old result shows that neither a one-layer speedup nor a runtime
cache hit rate can establish that condition.  A reviewer must either retain
that condition (in which case this proposal ends at an evidence-only NO-GO) or
approve the explicit scope amendment in [Decision required](#decision-required)
before an all-layer performance claim is attempted.

## Proposed sequence

### R1.0: Measurement harness only

Implement no new quantized execution path.  First add a release-process
benchmark wrapper that runs the unchanged `reference-f32-v1` path and emits a
versioned JSON record.  It must establish that the following fields can be
collected reliably before a candidate is created:

| Required evidence | Collection rule | Gate |
| --- | --- | --- |
| Process working set | An independent PowerShell sampler records `WorkingSet64` and `PrivateMemorySize64` every 100 ms; the report keeps the maximum of sampled working set and the process `PeakWorkingSet64` value after exit. | No missing sample, failed process, or unparseable value. |
| Candidate/accounted memory | The runtime reports expert payload, cache metadata, read buffers, KV cache, and candidate scratch separately. | Reconciles exactly with configured limits; never substitutes for process working set. |
| Logical reads | The artifact reader reports requested and returned byte ranges, cache hits/misses, and loads. | Existing cache reconciliation invariants pass. |
| Physical storage evidence | A separately saved ETW capture must contain process-correlated Kernel File and Disk I/O events for the benchmark PID and exact artifact file identities.  Process I/O counters alone are labelled logical/API I/O and are insufficient. | If event correlation, byte totals, or capture provenance cannot be demonstrated, physical I/O is `not_measured` and the proposal stops. |
| Cache state | The report labels runtime-cache state and OS filesystem-cache state independently.  No test calls an undocumented cache-dropping mechanism. | No “cold device” wording unless a reviewed and reproducible device-cache control exists. |

The R1.0 reference run is a validation of telemetry only.  It cannot be used
as a performance baseline until five independent clean processes have passed
the collection and reconciliation checks.

### R1.1: Deterministic candidate admission study

Only after R1.0 passes, generate and characterize candidate layouts in a
temporary, flat run directory under `docs/temp-artifact-policy.md`.  The study
may compare group sizes and storage precisions, but it must emit exactly one
selected candidate or the classification `no_candidate_admitted`; it must not
silently select a format after looking at final tokens.

The candidate selection record must include source manifest/revision/license,
conversion command and tool versions, tensor names/shapes, group axis/size,
rounding/saturation rules, byte order, layout offsets, source/output hashes,
and generation timestamp.  The normal execution path must consume the packed
values and scales directly; complete F32 projection or expert reconstruction
is forbidden.  Router, all norms, routing weights, residuals, softmax,
activations, and accumulation remain F32.

The selection record must pre-register these gates:

1. exact artifact structure, hashes, offsets, shapes, dtypes, and finite
   values;
2. deterministic re-conversion, byte-identical candidate artifact, and
   deterministic repeated candidate output;
3. exact router IDs for every router result whose F32 top-k boundary is safely
   separated according to the frozen margin rule; near ties remain classified
   as ambiguous rather than accepted as equal;
4. stage-by-stage Layer-0 checkpoint comparison with the first divergent
   operation named; and
5. candidate logit error bounded by both a pre-registered absolute/relative
   envelope justified from the characterization set and one quarter of each
   corresponding frozen F32 greedy top-1 margin.  The candidate must retain
   exact frozen top-20 IDs, greedy IDs, and multi-token sequences for every
   English and Thai quality fixture.

The numerical envelope is intentionally not a copy of the F32 tolerance
registry.  It must be proposed in the R1.1 ADR before candidate execution,
derived from held-out Qwen3 characterization cases, and validated on a
disjoint bilingual fixture set.  A threshold picked after observing the final
fixture is a failure.  Delta-NLL, top-k agreement, and endpoint agreement are
reported as additional quality evidence, never as substitutes for a failed
safe-margin or token gate.

### R1.2: Paired resource and I/O benchmark

Benchmark the single admitted candidate against the unchanged F32 path using
the same artifact, fixture, context, cache budget, release binary, and host.
Run five independent process pairs for each declared condition; alternate
candidate-first and reference-first order.  Runtime-cache-cold and
runtime-cache-warm are separate conditions.  OS cache state remains observed,
not assumed.

Every sample records wall time, TTFT, prompt/decode tokens/s, process working
set peak, sampled private peak, candidate/accounted peaks, logical byte
metrics, ETW-correlated physical read bytes, physical reads/token, cache
metrics, and ETW/PowerShell collector versions.  Any failed collector makes
the condition invalid rather than zero.

The resource gates are:

- Peak process working set is at or below the declared usable-RAM budget and
  has no unexplained increase above the explicit candidate payload, cache,
  scratch, and a 10% accounting allowance relative to the paired F32 run.
- Candidate resident bytes, scratch, and cache bytes are individually bounded
  and reconcile to the configured byte budget; mapped bytes, if any, are
  reported separately.  Memory mapping is not authorized by this proposal.
- Candidate physical reads/token are measured rather than inferred from
  logical reads.  An uncorrelated ETW trace, disk-wide counter, or unavailable
  capture is a no-go, not a zero-byte result.
- The median and each of the five paired deltas must point in the same
  direction for the claimed metric; report median, min/max, and paired percent
  change.  A win in cache hit rate alone is not a throughput win.

## Performance claim boundary

R1.2 may claim only a Layer-0 vertical-slice improvement.  It cannot claim a
material full-model decode gain, because unchanged Layers 1--47 dominate that
measurement.  No extrapolation from payload compression, expert read savings,
or a microbenchmark is permitted.

To promote a candidate beyond R1.2, a separately approved all-layer
implementation plan must retain the exact R1.1 format and rerun the quality,
working-set, and physical-I/O gates on the complete runtime.  This preserves
the distinction between a valid slice and an admitted product path.

## Decision required

Reviewers must choose one of the following before implementation:

1. **Evidence-only re-entry.** Approve R1.0--R1.2 solely to produce complete
   quality/resource evidence.  M6.4 remains blocked regardless of local
   speed results because the current M6.3 whole-runtime-benefit condition is
   retained.
2. **Amended M6.3 re-entry.** Approve R1.0--R1.2 and amend the implementation
   plan/tasks so M6.3 exits on an admitted, measured Layer-0 slice; then make
   a separate all-layer candidate plan prove the material end-to-end benefit
   before M6.4 is opened.  This is a milestone-contract change and requires a
   new ADR/task review.

The proposal recommends option 1 first.  It closes the missing evidence
without presuming that a new quantization layout is acceptable or that an
all-layer implementation is warranted.

## Explicit non-goals

- No CUDA, Vulkan, DirectML, FFI, SIMD, `unsafe`, memory mapping, async
  prefetch, thread pool, cache-policy replacement, or native kernel fusion.
- No Swift/Metal code or artifact layout is copied from TurboFieldfare.
- No full-model quantized artifact, M6.4 implementation, server, UI, or model
  family expansion.
- No tolerance is widened to admit a candidate.

## Required review artifacts before work starts

- A proposed ADR selecting the single candidate only after R1.0 telemetry is
  validated.
- A versioned benchmark JSON schema and validator covering all R1.0/R1.2
  fields and invalid/missing collector states.
- A PowerShell collection script with PID handoff, sampler cleanup, ETW start/
  stop commands, trace hash, and a dry-run mode.
- A temporary-artifact preflight/cleanup record for every candidate conversion.
- Updated `implementation-plan.md` and `tasks.md` only if reviewers select
  the amended M6.3 re-entry option.
