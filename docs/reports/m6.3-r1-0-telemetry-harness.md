# M6.3-R1.0 Release-Process Telemetry Harness

## Status

**Complete for R1.0.** The PowerShell collector, JSON contract, validator,
dry-run, cleanup path, and five full `reference-f32-v1` release processes were
exercised. An elevated `logman` witness captured all 49 canonical artifact
files with zero ETW event loss. Subsequent runs were explicitly recorded as
OS-filesystem-cache `uncontrolled` and physical I/O `not_measured` when no
Disk event was emitted; no logical bytes were substituted.

Per the reviewed re-entry protocol, physical I/O is recorded as
`not_measured`, never zero. M6.3-R1.1 did not start and no candidate artifact
was created.

## Implemented contract

- `scripts/m6_3_r1_0_telemetry.ps1` launches a clean release process, samples
  `WorkingSet64` and `PrivateMemorySize64` every 100 ms, retains the maximum of
  sampled working set and `PeakWorkingSet64`, writes stdout/stderr separately,
  and removes each unique temporary run directory in `finally`.
- Explicit runtime memory, logical/API reads, and cache metrics are distinct
  from process working set and physical I/O.
- Runtime-cache state and OS filesystem-cache state are separate; the latter
  is always `uncontrolled`.
- `docs/schemas/m6.3-r1-telemetry-v1.schema.json` defines the record shape.
- `scripts/validate_m6_3_r1_0_telemetry.py` rejects missing samples, failed
  processes, an uncontrolled-cache mislabel, missing ETW correlation, and any
  failed R1.0 gate.
- `scripts/capture_m6_3_r1_etw.ps1` runs an elevated `logman` session with
  explicit Kernel-File and Kernel-Disk providers, records the ETL hash and
  provider manifest hash, and invokes `parse_m6_3_r1_etw.py`.
- `scripts/parse_m6_3_r1_etw.py` requires exact PID plus artifact path/FileObject,
  then the provider-defined `Kernel File Read.FileKey = Kernel Disk.FileObject`
  join and a Kernel-Disk read byte count. It also requires `tracerpt` to report
  `Total Events Lost = 0`. It does not infer physical I/O from logical reads or
  disk-wide counters; an unavailable buffer-loss field is recorded as
  `not_reported`, never zero.

## Evidence

The dry-run completed without starting a model process. Four validator unit
tests and six parser tests passed, including collector-failure, cache-label,
encoding, PID, and double-counting regression cases.

Five independent `target/release/clr-cli.exe` smoke processes exited zero and
produced at least one independent memory sample each. These are collector
smoke runs only; they do not replace the required full `reference-f32-v1`
benchmark. The run record is
`docs/benchmarks/m6.3-r1-0-reference-telemetry-v1.json`.

The initial WPR probe result was:

```text
status: not_measured
reason: WPR start failed with access denied (0x80070005)
physical read bytes: null
```

The validator correctly rejects the record because `physical_io` is false.

The accepted witness (`run-20260731T173806Z-1f4407fd064a43c395313f057ea7c005`)
reported `Total Events Lost 0`. The corrected parser found `22,550` File reads,
`14,110` unique Kernel Disk events correlated through FileKey/FileObject, and
`28,822,028,288` physical bytes across all 49 artifacts. Each Disk event is
counted once; repeated logical reads sharing a FileKey are not multiplied.

The initial direct `logman stop` client could hang after the ETW session had
already ended, preventing finalization of that otherwise valid calibration.
The collector now bounds that client, verifies session disappearance plus an
ETL file before continuing, and exports CSV plus `tracerpt -summary` for each
capture. This revised stop path has not yet been exercised with an elevated
token in the current environment, so the calibration is not one of the five
acceptance runs.
